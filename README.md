# سامانه کنترل

سامانه مدیریت کالا با رابط فارسی و راست‌چین، با هدف ارائه و اجرای آزمایشی در محیط سازمانی.

## دستورالعمل‌ها و قوانین قطعی پروژه

> این جدول مرجع تصمیم‌گیری برای تمام توسعه‌های فعلی و بعدی پروژه است. هر قابلیت جدید باید با این قوانین سازگار باشد. در صورت تعارض، دستور صریح و جدیدتر کاربر ملاک است.

| ردیف | حوزه | قانون / دستورالعمل |
|---:|---|---|
| ۱ | دامنه تغییرات | فقط همان چیزی را پیاده‌سازی کن که کاربر درخواست کرده است. تغییر اضافه، بازطراحی خودسرانه، قابلیت پیشنهادیِ اجرا‌نشده یا تغییر در بخش‌های نامرتبط ممنوع است. |
| ۲ | روش توسعه | پروژه مرحله‌ای پیش می‌رود. پیش از تغییر، فایل‌ها و ساختار فعلی مخزن بررسی شوند؛ تغییرات باید با معماری و ظاهر موجود هماهنگ باشند. |
| ۳ | ثبت تغییرات | تغییرات تأییدشده مستقیماً روی شاخه `main` ثبت شوند. پیش از هر به‌روزرسانی، نسخه و SHA تازه فایل دریافت شود و پس از ثبت، نتیجه بررسی شود. |
| ۴ | زبان و جهت | تمام رابط کاربری فارسی و راست‌چین (RTL) باشد؛ متن‌ها، راهنماها، پیام‌ها و حالت‌های خالی روشن و قابل فهم باشند. |
| ۵ | محیط اجرا | سامانه برای محیط سازمانیِ بدون اینترنت و محدودیت نصب نرم‌افزار طراحی می‌شود. اجرای اصلی باید در مرورگر و بدون نیاز به نصب برنامه یا اتصال اینترنت ممکن باشد. |
| ۶ | منابع خارجی | برای عملکرد اصلی از CDN، فونت، کتابخانه، API یا منبع خارجیِ نیازمند اینترنت استفاده نشود. کتابخانه‌های لازم باید به‌صورت فایل محلی در مخزن نگهداری و از مسیر محلی بارگذاری شوند. |
| ۷ | معماری فعلی | تا زمان دستور جدید، راهکار ذخیره‌سازی محلی و آفلاین مبنا است؛ از IndexedDB استفاده شود. سرویس ابری، سرور، همگام‌سازی شبکه‌ای یا اتصال به پایگاه داده سازمان اضافه نشود. |
| ۸ | محدوده کاربر | وضعیت آزمایشی فعلی برای یک کاربر روی یک سیستم است. راهکار چندکاربره یا چنددستگاهی در این مرحله پیاده‌سازی نشود. |
| ۹ | ماندگاری داده | اطلاعات عملیاتی باید در ذخیره‌ساز محلی مرورگر باقی بمانند و صرفاً به حافظه موقت صفحه متکی نباشند. برای داده‌های کالا از لایه مشترک `assets/js/database.js` و API موجود `ControlDB` استفاده شود؛ ذخیره‌سازی پراکنده و ناسازگار ایجاد نشود. |
| ۱۰ | محدوده داده | IndexedDB به همان مرورگر و پروفایل کاربر محدود است و به‌خودی‌خود بین دستگاه‌ها همگام‌سازی نمی‌کند. این محدودیت در تصمیم‌های فنی لحاظ شود. |
| ۱۱ | پشتیبان‌گیری | پشتیبان‌گیری و بازیابی اطلاعات مطلوب است، اما تا وقتی کاربر صریحاً درخواست نکرده، قابلیت یا رابط آن اضافه نشود. |
| ۱۲ | اتصال سازمانی | در مرحله فعلی دسترسی به پایگاه داده شرکت وجود ندارد. برای اتصال آینده، کدنویسی یا زیرساخت فرضی اضافه نشود؛ اولویت فعلی نمایش عملکردهای سامانه است. |
| ۱۳ | مشخصات پایه کالا | هر کالا باید این مشخصات را داشته باشد: کد اختصاصی، کد تدارکاتی، شرح کالا، تعداد موجودی و گروه کالا. |
| ۱۴ | کد تدارکاتی | کد تدارکاتی باید دقیقاً ۱۰ رقم باشد. ارقام فارسی و عربی هنگام ورود، در صورت نیاز، به رقم استاندارد تبدیل و سپس اعتبارسنجی شوند. |
| ۱۵ | کد اختصاصی | کد اختصاصی دقیقاً برابر با ۸ رقم اول کد تدارکاتی ۱۰ رقمی است. هیچ هش، عدد تصادفی، شناسه مستقل یا الگوریتم جایگزین برای ساخت آن استفاده نشود. |
| ۱۶ | یکپارچگی کد | این قاعده کدگذاری باید در تمام روش‌های ورود، نمایش، ذخیره‌سازی و عملیات بعدی رعایت شود؛ کد اختصاصی نباید با کد تدارکاتی ناسازگار شود. |
| ۱۷ | اعتبارسنجی ورود | پیش از ثبت، فیلدهای ضروری و قالب داده بررسی شوند. کد نامعتبر، اطلاعات ناقص و کد تکراری نباید به‌عنوان کالای معتبر ثبت شوند. |
| ۱۸ | ورود از فایل | روش ورود فایل از Excel، CSV و JSON پشتیبانی کند؛ انتخاب فایل با کلیک و Drag & Drop ممکن باشد؛ پیش‌نمایش و نتیجه بررسی قبل از ثبت نمایش داده شود. |
| ۱۹ | ورود از فایل ـ ستون‌ها | فهرست پیش‌نمایش ورود فایل شامل ردیف، کد اختصاصی، کد تدارکاتی، شرح کالا، تعداد موجودی، گروه و وضعیت باشد. |
| ۲۰ | ورود از فایل ـ ثبت | فقط ردیف‌های معتبر ثبت شوند. ردیف‌های تکراری، ناقص یا نامعتبر در بخش مغایرت‌ها همراه با علت عدم ثبت نمایش داده شوند. |
| ۲۱ | ورود با کپی و پیست | داده‌های کپی‌شده از Excel یا جدول با ترتیب کد تدارکاتی، شرح کالا، تعداد موجودی و گروه پردازش شوند؛ وجود یا نبود ردیف عنوان تا حد امکان تشخیص داده شود. |
| ۲۲ | ورود با کپی و پیست ـ ثبت | قبل از ثبت، پیش‌نمایش و اعتبارسنجی نمایش داده شود. کد نامعتبر، شرح خالی، تعداد نامعتبر، گروه خالی و تکراری‌های داخل فایل یا موجودی شناسایی و گزارش شوند. |
| ۲۳ | ثبت دستی | فرم ثبت دستی باید چهار ورودی کد تدارکاتی، شرح کالا، گروه کالا و تعداد موجودی داشته باشد. کد اختصاصی از روی کد تدارکاتی ساخته شود و همان قواعد اعتبارسنجی و ذخیره‌سازی سایر روش‌ها رعایت شوند. |
| ۲۴ | فهرست موجودی | فهرست کل موجودی باید ستون‌های ردیف، کد اختصاصی، کد تدارکاتی، شرح کالا، گروه کالا و تعداد موجودی را نمایش دهد و داده‌ها را از ذخیره‌ساز محلی بخواند. |
| ۲۵ | مرتب‌سازی سراسری | هر جدول یا فهرستی که چند فیلد/ستون مشخص دارد باید امکان مرتب‌سازی برای تمام ستون‌ها و فیلدهای قابل نمایش را داشته باشد؛ این قانون برای همه بخش‌های فعلی و آینده الزامی است. |
| ۲۶ | رفتار مرتب‌سازی | کلیک روی عنوان ستون، مرتب‌سازی صعودی و کلیک مجدد روی همان ستون، مرتب‌سازی نزولی را اجرا کند. جهت مرتب‌سازی با نشانگر مشخص باشد. |
| ۲۷ | نوع مرتب‌سازی | مرتب‌سازی باید متناسب با داده باشد: اعداد به‌صورت عددی، متن با مقایسه متنی و کدها با حفظ ترتیب طبیعی انجام شوند. ارقام فارسی و انگلیسی تا حد امکان معادل در نظر گرفته شوند. |
| ۲۸ | سلامت داده هنگام مرتب‌سازی | مرتب‌سازی فقط ترتیب نمایش ردیف‌ها را تغییر دهد؛ مقدار داده‌ها، شناسه‌ها و محتوای ذخیره‌شده نباید تغییر کند. |
| ۲۹ | ستون ردیف | اگر جدول ستون شماره ردیف دارد، پس از مرتب‌سازی شماره ردیف باید با ترتیب جدید نمایش هماهنگ باشد و شماره قدیمیِ وابسته به ترتیب قبلی باقی نماند. |
| ۳۰ | منوی اصلی | ترتیب سکشن‌های اصلی ثابت باشد: ۱) داشبورد، ۲) ورود کالا، ۳) مشاهده کالاها و موجودی، ۴) ارسال کالا، ۵) کاردکس، ۶) گزارش‌ها، ۷) تنظیمات و مدیریت. |
| ۳۱ | زیرمنوی ورود کالا | زیرمجموعه‌های ورود کالا بلافاصله زیر عنوان آن نمایش داده شوند: ورود از فایل Excel / CSV / JSON، کپی از جدول، ثبت دستی کالا. همین ساختار در صفحات زیرمجموعه نیز حفظ شود. |
| ۳۲ | طراحی منو | سایدبار باید گروه‌بندی‌شده، مدرن، کاربرپسند، واکنش‌گرا و قابل باز و بسته‌شدن باشد. شماره سکشن‌ها در نشانگر کوچک نمایش داده شوند؛ سکشن فعال نشانگر فیروزه‌ای روشن و درخشان و زیرمجموعه فعال نشانگر کهربایی/زرد داشته باشد. |
| ۳۳ | هویت بصری | قالب کلی روشن با پس‌زمینه آبی‌ـ‌خاکستری، هدر سفید، سایدبار سرمه‌ای با گرادیان و رنگ تأکیدی فیروزه‌ای باشد؛ طراحی صفحات جدید با این هویت هماهنگ بماند. |
| ۳۴ | طراحی فرم‌ها | فرم‌ها و فهرست‌ها مرتب، خوانا و کاربرپسند باشند. چیدمان در نمایشگر کوچک به‌درستی واکنش‌گرا شود و جدول‌های عریض امکان پیمایش افقی داشته باشند. |
| ۳۵ | راهنمای صفحه | در صفحات ورود اطلاعات، راهنمای کوتاه و روشن در ابتدای محتوای اصلی و پس از لینک بازگشت قرار گیرد؛ مراحل و الزامات ورود را توضیح دهد. |
| ۳۶ | تقویم | تاریخ‌های موردنیاز سامانه بر مبنای تقویم شمسی نمایش داده شوند. از کتابخانه محلی `assets/js/jalali-calendar.js` و API آن استفاده شود؛ برای ورودی تاریخ از ویژگی `data-jalali-calendar` استفاده شود. |
| ۳۷ | فیلدهای عملیاتی | در بخش‌های عملیاتی مرتبط، فیلدهای محل ارسال، تاریخ، شماره حواله، شماره خروج و شماره ورود در صورت اقتضای همان عملیات لحاظ شوند؛ فیلد نامرتبط یا اضافی خودسرانه اضافه نشود. |
| ۳۸ | فایل‌ها و ساختار | فایل‌های هر بخش مطابق ساختار موجود در پوشه همان سکشن نگهداری شوند؛ منطق مشترک در فایل‌های مشترک `assets/js` و استایل عمومی در `assets/css/style.css` قرار گیرد، نه اینکه نسخه‌های متناقض و تکراری ساخته شود. |
| ۳۹ | کتابخانه Excel | برای پردازش Excel از نسخه محلی موجود در `assets/libs/xlsx.full.min.js` استفاده شود و فایل مجوز آن حفظ شود. |
| ۴۰ | سازگاری | قابلیت‌های جدید باید با مرورگرهای سازمانیِ هدف و محدودیت آفلاین سازگار باشند؛ برای قابلیت اصلی به نصب افزونه یا نرم‌افزار جدید وابسته نشوند. |
| ۴۱ | پیام‌ها و خطاها | عملیات در حال اجرا، موفقیت، خطا، فهرست خالی و مغایرت‌ها باید با پیام قابل فهم به کاربر اعلام شوند؛ خطاها پنهان یا به‌اشتباه موفقیت گزارش نشوند. |
| ۴۲ | آزمون و گزارش نتیجه | پس از تغییر، فایل‌ها و مسیرهای بارگذاری بررسی شوند. فقط آزمون‌هایی که واقعاً اجرا شده‌اند گزارش شوند؛ بدون آزمون مرورگری، ادعای تست کامل یا عملکرد قطعی مرورگر مطرح نشود. |
| ۴۳ | مستندسازی | هر قانون قطعی جدیدی که کاربر اعلام کند، پس از تأیید معنای آن در همین جدول به‌روزرسانی شود تا مبنای توسعه‌های بعدی باشد. |
| ۴۴ | یکپارچگی طراحی | هر جزء جدید رابط کاربری، از جمله دکمه‌ها، فرم‌ها، پیام‌ها، کارت‌ها و فهرست‌ها، باید از هویت بصری، رنگ‌بندی، فاصله‌گذاری، گوشه‌ها، تایپوگرافی و رفتار تعاملی مشترک کل سامانه تبعیت کند؛ هیچ جزء پیش‌فرض یا ساده و ناهماهنگ اضافه نشود. |

## ساختار فعلی پروژه

- `index.html`: داشبورد
- `assets/css/style.css`: استایل عمومی و هویت بصری
- `assets/js/app.js`: رفتار عمومی رابط
- `assets/js/database.js`: لایه ذخیره‌سازی محلی IndexedDB
- `assets/js/jalali-calendar.js`: تقویم شمسی
- `assets/js/table-sort.js`: مرتب‌سازی مشترک جدول‌ها
- `assets/libs/`: کتابخانه‌های محلی
- `sections/vorood-kala/`: بخش ورود کالا و روش‌های ورود از فایل، کپی و پیست و ثبت دستی
- `sections/moshahede-kala/`: مشاهده کالاها و موجودی
- `sections/ersal-kala/`: ارسال کالا
- `sections/kardex/`: کاردکس
- `sections/gozaresh-ha/`: گزارش‌ها
- `sections/modiriat/`: تنظیمات و مدیریت

## وضعیت فعلی پیاده‌سازی

این قسمت وضعیت موجود مخزن را از قوانین هدف جدا می‌کند تا مستندات، قابلیت ناتمام را به‌عنوان قابلیت تکمیل‌شده معرفی نکنند.

| بخش | وضعیت ثبت‌شده در مخزن |
|---|---|
| ذخیره‌سازی کالا | IndexedDB و لایه مشترک `ControlDB` ایجاد شده‌اند. |
| ورود از فایل | پردازش محلی Excel / CSV / JSON، پیش‌نمایش، اعتبارسنجی و ثبت کالاهای معتبر پیاده‌سازی شده است. |
| کپی از جدول | تحلیل داده، پیش‌نمایش، اعتبارسنجی و ثبت کالاهای معتبر پیاده‌سازی شده است. |
| ثبت دستی | فرم چهار فیلدی با اعتبارسنجی کد تدارکاتی، جلوگیری از ثبت تکراری، ثبت در IndexedDB و ایجاد گردش ورود کاردکس پیاده‌سازی شده است. |
| مشاهده موجودی | فهرست کالاها از IndexedDB خوانده و نمایش داده می‌شود. |
| مرتب‌سازی | فایل مشترک مرتب‌سازی ایجاد شده و به صفحه موجودی و صفحات ورود از فایل و کپی‌پیست متصل شده است. |
| مدیریت کالاها | زیرمجموعه مدیریت کالاها با جست‌وجوی کد/شرح، حذف موردی و حذف کلی کالاهای موجودی پیاده‌سازی شده است؛ حذف کالا، سوابق کاردکس و ارسال‌ها را پاک نمی‌کند. |
| تقویم شمسی | کتابخانه محلی آن وجود دارد؛ اتصال آن باید در صفحات دارای فیلد تاریخ انجام شود. |
